multi-thread

We can build a thread-management-runtime crate to implement the support of thread base on user mode.
Thread is composed of thread-id,thread-status,current_PC,registers and stack,which is regarded as the basic unit of scheduling and dispatching for os or user mode(schedular).
But the defect about the implement of user mode thread scheduler is that only the thread voluntarily give up the CPU can the thread-management-runtime check.

In the past few chapters, the each process has their owned virtual address ,and kernel limit the time slice for each process.So the communication of each process needs the kernel to intervene.Now each process have multiple thread which regards as a execute point for this thread with shared virtual address.This may be convenient for thread to access the data to collaborate.

The first build thread has a TID,which always fix to 0.

We used RecycleAllocator in the past,and we continue to use it to allocate several resource with RAII style,which could be dropped to implement the automatic resource recycling.
The process allocator has the same allocator as before,like RecycleAllocator,and each PCB has a owned RecycleAllocator for thread.

Except for the allocator,each thread still need their owned user stack and Trap context,which can calculate by their TID.

formula:

id.rs

Thread’s TID,user stack, and Trap context all have the same lifecycle as the thread,so we can package them together for unified allocation and recycling.

We need a boolean var: alloc_user_res,to control the usage of function alloc_user_res.Because when fork the sub process and build the main thread,it doesn’t need to alloc the user stack and trap context.

Implement the RAII:

KernelStack would not relate to the PID or TID,even though the kernel layout is same as before.Rather,it relates to a new kernel stack identifier. We need to add a new generic resource allocator called KSTACK_ALLOCATOR to allocate kernel stack identifiers.

As the most important parts in thread mechanism,this concludes resource allocator and allocation and reclamation mechanisms for the three types of hardware and software resources.

在实现了阻塞唤醒机制之后，就可以实现sleep调用，当user调用的时候，就会trap into kernel，然后此线程将被阻塞。直到时钟计数器的值超过当前时间加上线程睡眠时长的总和。

每次时钟中断的时候检查阻塞队列里超时的线程，并移除，可以使用小根堆来实现，这样每次时钟中断的时候不断弹出堆顶直到堆顶没有超时即可
为TimeCondVar定义一些PartialEq, Eq, PartialOrd, Ord 这些 Trait 。

时钟中断的时候会调用此函数尝试唤醒睡眠超时的线程

至于信号量的实现，也是封装了一个Semaphore类，以及inner，来实现的。
inner里面会有一个count和一个wait_queue（VecDeque），这个Semaphore支持new up down两个操作，根据这个count来实现的
