AI 时代不是“信息更多了”，而是噪音爆炸。一套“检索与筛选的作战系统”，会让你不被教程/营销/碎片化答案拖着走。

下面我给你一套你可以长期复用的：检索 → 过滤 → 验证 → 沉淀流程（偏工程师风格，适合你这种喜欢搞清楚原理的人）。

1）先定规则：你要找的不是“资源”，是“证据”

很多人搜资源的姿势是：搜到一个教程就开始学。
更稳的姿势是：先把你要解决的问题写成可验证的任务。

例子（WebServer）：

  • “我想学网络编程” ❌（太大）
  • “我要写一个 TCP echo，recv 返回 0 代表什么？” ✅（可验证）
  • “epoll LT/ET 的区别是什么？会导致什么 bug？我怎么复现？” ✅

你每次检索都围绕一个可验证问题，效率直接翻倍。

2）信息源分层：从“权威”到“经验”

你要学会分辨信息的等级。建议按这个优先级：

S级：标准/手册/官方文档（最可信）

  • man pages（Linux 系统调用）
  • RFC（协议标准，如 HTTP/TCP）
  • 官方文档（微软 WSL、gcc、cmake 等）

用途：定义、行为、边界条件、错误码
缺点：不好读，但它是“最终裁判”。

A级：经典教材/讲义（稳定、体系化）

  • OSTEP（OS）
  • TCP/IP 详解
  • Linux 高性能服务器编程

用途：解释“为什么” + 构建心智模型
缺点：慢，但能把你从“会用”拉到“会解释”。

B级：高质量工程博客/开源项目（最贴近实践）

特征：有代码、有数据、有复现步骤、有对比、有局限性说明。

用途：工程实现、踩坑经验、性能调优
缺点：可能过时，需要你验证。

C级：论坛/问答/短视频（只拿线索，别当答案）

用途：快速获得关键词、方向
缺点：错的很多、语境缺失、抄来抄去。

一句话总结：

你可以从 C级 获得“关键词”，但必须回到 S/A/B 去确认。

3）检索的“5种意图”，你要先选对

你搜东西之前先问自己：我是在找哪一种？

  1. 定义/语义：某 API/概念到底什么意思
  2. 教程/入门：如何从 0 跑通
  3. 最佳实践/工程方案：常见架构怎么设计
  4. 排错：某报错/bug 怎么定位
  5. 对比/取舍：A vs B，为什么这样选

不同意图对应不同 query 结构（下面给模板）。

4）你可以直接照抄的“检索模板”（工程向）

A. 找定义/语义（最容易被胡说骗）

模板：

  • man recv return 0 meaning
  • POSIX read returns 0
  • RFC 793 TIME_WAIT purpose

技巧：加上 man / POSIX / RFC / linux man-pages 这种词，会把你拉向权威来源。

B. 找最小可运行示例（你开工需要这个）

模板：

  • tcp echo server c++ minimal example linux
  • socket bind listen accept example
  • Beej guide socket example

技巧：一定加 minimal / from scratch / example
避免搜到“框架级大项目”把你吓到。

C. 学一个模块的“正确姿势”（工程化）

模板：

  • thread pool c++ condition_variable bounded queue
  • reactor pattern epoll c++ design
  • http parser state machine c++

技巧：加 design / tradeoff / pitfalls
你会更容易搜到“解释取舍”的内容，而不是纯代码堆砌。

D. 排错（你会大量用到）

模板：

  • accept EMFILE too many open files
  • send SIGPIPE broken pipe
  • epoll ET missing events bug

技巧：搜索时把“原始错误信息”原封不动贴进去，命中率最高。

E. 性能与调优（区别高手和菜鸟）

模板：

  • wrk qps latency p99 meaning
  • perf record flamegraph c++ server
  • strace network server slow

技巧：加 benchmark / profiling / p99
直接过滤掉大部分“泛泛而谈”。

5）筛选质量：10秒判断一篇文章值不值得读

你打开一个网页，快速看这几点：

高质量特征：

  • 有明确的前提（系统版本、环境）
  • 有可复现步骤（命令、代码）
  • 有数据/对比（压测结果、图）
  • 有失败情况/局限性（不是只讲成功）
  • 有引用/链接到官方文档/RFC/man

低质量特征：

  • 标题党、营销口吻、全是“最佳/最强/必学”
  • 只有结论没有推导，没有复现
  • 代码贴一坨，没有解释边界条件
  • 评论区一堆人在纠错

你是“想搞明白为什么”的人，所以优先找“讲边界条件”的内容。

6）AI 在检索里怎么用才不坑你（关键）

AI 最容易坑你的地方：它给你“看起来合理但缺乏证据”的答案。

你应该这样用 AI：

正确用法 1：让 AI 给“关键词 + 检索路径”

你问：

  • “我正在实现 epoll reactor，你给我需要查的 man page 列表 + 关键错误码 + 验证实验”

正确用法 2：让 AI 帮你“读文档/提炼重点”

你把一段 man page / RFC 粘给 AI：

  • “请解释这段在说什么，用例是什么，常见坑是什么”

正确用法 3：让 AI 帮你“设计验证实验”

你问：

  • “我怀疑是半包/粘包，给我一个最小复现方案和验证方法”

错误用法（尽量别这样）

  • “直接给我最正确的做法/最佳实现”
    因为没有上下文，AI 可能生成“教科书式正确但工程上不可靠”的方案。

一句话：

AI 负责加速你的“理解与路线”，证据要靠你跑实验/查手册确认。

7）沉淀系统：你要建立自己的“知识库”，不然永远重复搜

你只需要一个简单结构（用 Markdown 就够）：

  • 00_index.md：你在做的项目/当前卡点
  • 01_sockets.md：socket API、常见错误码、踩坑
  • 02_concurrency.md：线程池、锁、条件变量坑
  • 03_epoll.md：ET/LT、非阻塞、常见漏事件原因
  • 04_debug_tools.md：gdb/strace/perf 常用命令模板

每次解决一个问题，把“结论 + 复现命令 + 参考链接标题”记 10 行。
两个月后你会发现自己已经“像系统人”了：因为你有自己的证据库。

8）给你一个“今天就能用”的检索任务示例（以 echo 为例）

你准备写 echo server，然后你会遇到这些必搜点：

  1. recv return 0 meaning
  2. send SIGPIPE（为什么会崩）
  3. short write send partial
  4. tcp half close FIN ACK behavior（可选）
  5. man accept EAGAIN（后面非阻塞会用）

你把这些关键词先记到 01_sockets.md 里，就是你的第一块知识库。

如果你愿意，我可以把你 WebServer 的“第一周开工清单”直接变成一个检索任务列表（每条带：该搜什么关键词、该看哪个 man page、该做哪个小实验验证），你按任务打勾推进就行。你现在用的是 Windows + WSL 吗？还是已经有 Linux 环境？

9）什么时候适合直接问 AI（你现在这种情况就很适合）

可以，而且在你“完全没概念”的阶段，把问题抛给 AI 让它帮你搭一个最小框架是非常高效的做法——前提是你要用对方式：让 AI 产出“骨架+术语+下一步”，而不是“直接给你一坨完整实现”。

我给你一个可执行的规则：

AI 负责“定向+搭骨架”，权威资料负责“校准语义”，代码负责“验证”。

  • 你连这个东西是什么都不知道（TCP echo、epoll、线程池、HTTP parser）

  • 你不知道有哪些组件、顺序是什么

  • 你不知道应该搜什么关键词

这时 AI 最擅长：把一团雾变成一个可行动的目录。

10）但要注意：AI 搭骨架必须满足 3 个输出，否则你会被带偏

你问 AI 时要明确要求它输出：

  1. 一张“调用/流程顺序图”（或用列表表示也行）
  2. 每一步一句话解释 + 输入输出/返回值语义
  3. 你下一步该做的最小实验/最小代码骨架（可跑的那种）

并且让它附带：需要查的权威点清单（man page/RFC/官方文档），用于你后续校准。

11）你应该怎么问（直接照抄模板）

以后遇到任何新主题 X，都用这套提问：

我对 X 完全没概念。请用“最小认知骨架”的方式讲解：

  1. X 是什么、解决什么问题（不超过5句话）；
  2. 给我一个最小流程图/步骤序列（从开始到结束）；
  3. 列出每一步的关键 API/术语，并说明返回值/失败时意味着什么（只列最重要的）；
  4. 给我一个“最小可运行版本”的骨架（伪代码即可），并列出我需要自己补的地方；
  5. 最后给我 5 个我应该去查的权威入口（man page / RFC / 官方文档关键词），用于校准你刚才讲的内容。

这会把 AI 从“输出大段代码”强制拉回“搭框架”。

12）AI 搭完骨架后，你下一步必须做的“校准动作”（非常关键）

你不需要立刻啃书，但你要做一个“校准”来防止 AI 说错：

  • 对 Linux API：去看对应 man 页的 SYNOPSIS + RETURN VALUE
  • 对协议：找 RFC/权威教程里对应小节，确认语义
  • 对概念：找一个权威来源确认“定义”

这一步只要 10 分钟，但能避免你在错误理解上写一整天代码。

13）最佳实践：AI 解释 + 你自己画一张更小的图

AI 给你流程后，你自己用一句话把它再压缩一遍，比如 TCP echo：

  • Server：socket → bind → listen → accept → loop(recv→send) → close
  • Client：socket → connect → send → recv → close

你自己写出来，这一步会让框架“落到你脑子里”，而不是停在 AI 的文字里。

14）什么时候不建议把“从零学习”完全交给 AI

  • 你进入“精确语义/边界条件”阶段（例如：EINTR/EAGAIN、半包粘包、ET 模式正确性）
  • 你开始做性能/正确性承诺（例如：不会漏事件、不会死锁、不会泄漏 fd）

这时候 AI 仍能帮你列坑、给排查路线，但裁判必须是 man/RFC + 实验验证。

15）一个很实用的策略：让 AI 先给你“关键词地图”

你说你不会在网络时代找资源，那 AI 的一个超强用法是：

“给我 10 个关键词/术语 + 每个术语对应我该搜什么（man page 名称 / RFC 号 / 经典资料章节）”

它会把你的“不会搜”变成“可搜索的词”。

16）结论

  • 可以直接抛给 AI，让它帮你建立最小框架，这是你现在最该用 AI 的地方。
  • 但你要用“骨架式提问”，并且搭完骨架立刻用 man/官方文档做 10 分钟校准。

如果你愿意，我们就拿“TCP echo”做一次完整示范：
你把你现在的理解（哪怕一句话）发我，我按上面的 5 点输出一个最小框架，然后我再给你对应的 5 个权威入口关键词，你就能立刻开始写第一版代码。
